# Tofu gallery copy

This repository is Tofu's copy of **reactive-resume/reactive-resume** (licence: MIT), listed in Tofu's app gallery as **Reactive Resume**: a resume builder. You write your resume in an editor beside a live preview, choose one of its 18 templates, download it as a PDF (or Word, Markdown or JSON), and share a link to it that anyone can open.

- `main` mirrors the upstream repository and is never committed to by Tofu.
- `tofu` carries Tofu's own changes; tags named `pin/<date>` (with `.1`, `.2` and so on for a later pin the same day) mark the versions the gallery points to, and a new copy takes the newest. Tags are never moved.
- A visitor who chooses this app gets a private snapshot of the pinned version in their own Tofu account. Their copy does not follow upstream updates.
- Upstream: https://github.com/reactive-resume/reactive-resume at `5d247c59de925b04e6e658300524812c7f544ec4`, the head of `main` on 2026-10-25: release v6.0.6 plus five commits (two small fixes, a documentation change, the Cloudron catalog entry and the mobile release workflow).

## How Tofu runs it

- Framework preset `container`, root folder: the repository root. Tofu builds the root `Dockerfile` and runs the image as a service, so there is no separate install command, build command or output directory.
- The `Dockerfile` is upstream's, with only its last stage's start changed (below). Its stages:
  - `base`: `ghcr.io/pnpm/pnpm:12.14.0`, which switches itself to the pnpm that `package.json` names (12.15.0), with Node 24 from `pnpm runtime set node 24`.
  - `pruner`: `turbo prune web server --docker`, the web app and the server with the workspace packages they use.
  - `builder`: `pnpm install --frozen-lockfile`, then `pnpm turbo run build --filter=web --filter=server`: Vite builds the web app into `apps/web/dist` and its prerendered pages into `apps/web/dist-prerender`, and tsdown bundles the server into `apps/server/dist`.
  - `runtime-pruner` and `runtime-deps`: the server's production dependencies (`pnpm install --prod`).
  - The image, on `node:24-slim`: the builds, the dependencies and `migrations/`, started with `node apps/server/dist/index.mjs` through `tofu-entrypoint.sh`. The stages use BuildKit cache mounts (`RUN --mount=type=cache`).
- One Node process (Hono) serves the web app, its API, the shared resume pages, the PDFs and the uploaded pictures.
- Database: PostgreSQL, the copy's Tofu database, read from `DATABASE_URL`. The server runs its own Drizzle migrations (`migrations/`, 40 of them) at every start, holding a PostgreSQL advisory lock, and then Tofu's step in `apps/server/src/startup/tofu-database.ts` (below). There is no `supabase/migrations` folder, so Tofu applies nothing before the build.
- Settings: Tofu sets `PORT` and `DATABASE_URL` (it also saves `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SUPABASE_CA_CERT`, which the app does not read). The gallery saves `APP_URL`, the copy's own address, before its first deploy: Reactive Resume uses it for its sign-in callbacks, the links it shares, its social cards and the addresses of uploaded pictures, and requires it. Nothing has to be set by hand.
- Secrets: `AUTH_SECRET` and `ENCRYPTION_SECRET` are derived from `DATABASE_URL` when they are not set (each is the SHA-256 of a fixed label, a newline and the URL; see `tofu-entrypoint.sh`), so a copy needs no secret setting and restarts and redeploys keep them. `AUTH_SECRET` signs every session and sign-in token, and Better Auth encrypts with it what it keeps encrypted, including each person's two-factor secret and backup codes. `ENCRYPTION_SECRET` encrypts the AI provider keys people save in Settings. If `DATABASE_URL` changes (a restored or moved database), both change unless they were set by hand:
  - everyone has to sign in again, and saved AI provider keys have to be entered again;
  - **anyone who turned on two-factor sign-in can no longer sign in with their password at all.** Better Auth (1.7.12) can no longer decrypt their authenticator secret or their backup codes, so neither a code nor a backup code checks out, and turning two-factor sign-in off or setting it up again needs a signed-in session. Only a passkey, or an OAuth provider the owner set up and that person had linked, still gets them in, because the code is asked for only after a sign-in with a password (`/sign-in/email`, `/sign-in/username` and `/sign-in/phone-number`). A password reset helps only once SMTP is set up and only someone whose address was never verified: only then does it clear two-factor sign-in (`onPasswordReset` in `packages/auth/src/config.ts`). What lets the others in again is putting the old `AUTH_SECRET` back (a derived one is the SHA-256 above, of the old `DATABASE_URL`), or, over a database connection, deleting their row in `two_factor` and setting `"user".two_factor_enabled` to false.

  So an owner who wants two-factor sign-in on their copy should save their own `AUTH_SECRET` (at least 32 characters, for example the output of `openssl rand -hex 32`) as a hidden value on the app's Keys & settings page before anyone turns it on. Saving one later is itself such a change: it signs everyone out once and locks out whoever already uses two-factor sign-in. An owner who wants saved AI provider keys to survive a database move saves their own `ENCRYPTION_SECRET` (at least 32 characters) the same way.

## What Tofu changes

Every commit on `tofu` starts with `Tofu:` and says why. Every changed file carries a `Tofu (2026-10-25)` note at the change.

- **Removed for size.** Tofu imports a repository from GitHub's ZIP archive of one commit, at most 50 MB, and upstream's is about 56 MB. Removed: `docs/images` (the documentation site's pictures, two of which upstream's `README.md` shows: on this branch its editor picture and one sponsor's logo do not load) and `docs/spec.json` (written by `pnpm docs:gen`; the server makes `/api/openapi/spec.json` itself). The build and the running app read neither of them. Upstream's eight screenshots in `apps/web/public/screenshots` stay, although an earlier pin removed them: the web app's `manifest.webmanifest` lists them for the browser's install dialog, so a copy serves them. The mobile app (`apps/mobile`) stays: the archive is under the limit with it, and Tofu does not build it.
- **Upstream's `vercel.json` is removed.** It set up upstream's own deployment as Vercel Services: a separate web and server service, a 300-second limit for one request, and a job that calls `/api/career/run` every minute. A copy is built from the `Dockerfile`, which never reads it, but Tofu reads a root `vercel.json` before it deploys: on the Free plan and the free trial it refuses an app whose `vercel.json` declares scheduled jobs (`crons`), and on the Free plan a request limit above 60 seconds, so every Free or trial owner's copy would have been refused before anything was made. On the Pro plan it would have gone to the host beside the container build, a combination never tried. Nothing needs it: the server's own scheduler checks scheduled job searches once a minute (`apps/server/src/startup/career-scheduler.ts`), and `/api/career/run` answers 404 while `CRON_SECRET` is unset. Upstream's other hosting files (`apps/server/vercel.mjs`, `wrangler.jsonc`, `.vercelignore`) stay; nothing reads them on Tofu.
- **Uploads are kept in PostgreSQL.** A copy has no disk that outlives a restart, so upstream's local storage (`/app/data`) would lose every picture and saved PDF at the next redeploy. A new storage backend, `STORAGE_BACKEND=database` (`packages/api/src/features/storage/database.ts`, wired in `packages/api/src/features/storage/service.ts` and `packages/env/src/server.ts`), keeps each file as one row of the table `tofu_storage_object`, with the S3 backend's rules for keys and folders. The server makes the table at start, after the migrations (`apps/server/src/startup/tofu-database.ts`, called from `apps/server/src/startup/checks.ts`).
- **Row-level security for Supabase's Data API.** The same start-up step turns row-level security on, with no policy, for the app's own tables in `public` that do not have it yet, on a database that has Supabase's Data API roles (`anon` and `authenticated`). Tofu's databases are Supabase PostgreSQL, and one whose default privileges still give every new table in `public` to those roles would otherwise let anyone holding the project's public key read and change these tables through the Data API: accounts, sessions, password hashes and every resume. With row-level security on and no policy, those roles see no row; the app's own connection owns the tables, so nothing changes for it. The step never turns row-level security off, touches only tables the app's role owns, does nothing on a PostgreSQL without those roles, and a failure is logged without stopping the server. Its log line is `Enabled row-level security on <n> tables for Supabase's Data API`.
- **`tofu-entrypoint.sh` (new), and the `Dockerfile`'s start.** The image starts through it with `/bin/sh` (files Tofu deploys arrive without their execute bit), and it ends by starting the server. Upstream's `apps/server/docker-entrypoint.sh`, which switches to the `node` user, is no longer used: Tofu sends traffic to `PORT`, which is 80 unless the app sets another, and only root may listen on a port below 1024, so the server runs as root, as the image starts. Before starting the server it:
  - derives `AUTH_SECRET` and `ENCRYPTION_SECRET` when they are unset (above);
  - turns `sslmode=require` (or `prefer`) in `DATABASE_URL` into `sslmode=no-verify`. node-postgres reads `require` as full certificate verification, which fails against a managed database's pooler; `no-verify` encrypts without checking the certificate, which is what `require` means to libpq. A URL with its own `sslrootcert` is left alone;
  - when `DATABASE_MIGRATION_URL` is unset and `DATABASE_URL` names a pooler host (a `.pooler.` label) on port 6543, the pooler's transaction mode, sets `DATABASE_MIGRATION_URL` to the same URL on port 5432, its session mode. The migrations hold a session-level advisory lock, which a transaction pooler cannot keep: its unlock may run on another server connection and leave the lock held for the next start;
  - sets `STORAGE_BACKEND=database` unless S3 is configured.
  A value the owner sets is always kept.
- **Resume updates are heard on a session connection.** Without Redis, an open builder hears of changes made elsewhere (another tab, the assistant, the API or MCP) through PostgreSQL `LISTEN`, which needs a connection that keeps its session; through the transaction pooler no notification would arrive. When `DATABASE_MIGRATION_URL` is set, listening uses one connection of its own from it (`getListenPool` in `packages/db/src/client.ts`, used by `packages/api/src/features/resume/events.ts`). Notifications are still sent through the app's own pool.
- **No donation requests.** Upstream shows a donation pop-up after five minutes on any page but the builder, and a donation request under the Download button after each download. Both are gone (`apps/web/src/routes/__root.tsx`, `apps/web/src/features/resume/share/download-tab.tsx`; `apps/web/src/components/ui/donation-toast.tsx` and its test are removed). The project's own links in Settings, and the sponsor links on the homepage, stay. Reactive Resume has no analytics or trackers to remove, and nothing in it checks for updates.
- **No Context7 site key.** Every page upstream serves carried the site key of upstream's Context7 account three times: a `context7-site-verification` tag, a `Link` header pointing to Context7's search endpoint, and a hidden note sending AI agents to rxresu.me's `llms.txt` and that endpoint. `/llms.txt` named the endpoint too, and `context7.json` held the account's public key. The verification tag would let upstream's account claim a copy's address as one of its own sites. All of it is gone (`apps/server/src/static/seo.ts`, `apps/server/src/static/web.ts` and their tests), and `context7.json` is removed. People never saw any of it on the page.

## Signing up

- Reactive Resume has its own accounts (Better Auth), not Tofu's sign-in: email and password, and Google, GitHub, LinkedIn, Apple or another OAuth provider once the owner adds that provider's client ID and secret (`GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, and so on; see `.env.example`). Passkeys and two-factor sign-in are built in.
- **No account is an administrator.** Every account sees only its own resumes, letters and applications; the app has no page that manages other people's accounts.
- **Anyone who can open the address can sign up until sign-up is closed**, and keep their resumes in the owner's database. The owner should make their own account first, then save `FLAG_DISABLE_SIGNUPS` as `true` on the app's Keys & settings page and deploy again: the sign-up page then sends people to the sign-in page, which shows no sign-up link, and the server refuses new accounts (`Email and password sign up is not enabled`) by email and through OAuth alike. Existing accounts keep signing in. Shared resume links keep working for everyone.
- **No email is sent until SMTP is set up, and the pages say so.** A new copy has no SMTP settings, so it sends no email: the server logs only that it skipped one. The pages that would promise an email say this instead, using the app's own `smtpEnabled` flag (`/api/openapi/flags`):
  - after signing up, the step that would say "Check your email" says the account is ready and that no verification link was sent. Verifying is optional; the account works without it;
  - the Forgot password page shows, in place of its form, that this copy can't send email, so it can't send a reset link.
  Both name what turns email on: its owner saves `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER` and `SMTP_FROM` as settings and `SMTP_PASS` as a hidden value (`apps/web/src/features/auth/pages/register.tsx` and `forgot-password.tsx`, with the shared note in `apps/web/src/features/auth/components/email-settings-note.tsx`). Until then nobody can reset a forgotten password, so an owner should keep their password safe, or add the settings first. Email is sent once the host, user, password and sender are all set (`SMTP_PORT` defaults to 587 and `SMTP_SECURE` to false), and the server starts without any of them. The gallery names `SMTP_PASS` as a hidden value only the owner can supply. The six new messages are in every catalog in `apps/web/locales`, untranslated, so every language shows them in English; the catalogs were refreshed with the repository's own `lingui extract --clean --overwrite`, which also dropped the four donation messages removed above.

## What works differently on Tofu

- **Uploaded files (pictures, the assistant's attachments) and the PDFs of shared resumes are kept in the database** and count toward its size. A picture is resized to at most 800 pixels and saved as a JPEG; the upload limit is upstream's 10 MB. To keep files in S3-compatible storage instead, save `S3_ACCESS_KEY_ID`, `S3_BUCKET`, `S3_REGION`, `S3_ENDPOINT` and `S3_FORCE_PATH_STYLE` as settings and `S3_SECRET_ACCESS_KEY` as a hidden value; files already in the database are not moved, so pictures uploaded before the switch stop showing until they are uploaded again.
- **PDFs need no headless browser.** Reactive Resume makes them with its own PDF engine (`@formepdf`, WebAssembly): in the browser for the builder's Download button, and on the server for the Download button of a shared resume, whose PDF is kept in storage and made again after the resume changes. Fonts the app does not bundle are loaded from Google Fonts.
- **AI features wait for a key.** The assistant, writing help, resume review, job matching and scheduled job searches need an AI provider. Each person can add their own provider and key in Settings, kept encrypted with `ENCRYPTION_SECRET`. An owner can instead set one provider for everyone: `AI_PROVIDER` and `AI_MODEL` as settings and `AI_API_KEY` as a hidden value. Save all three before deploying: with only some of them the server refuses to start. Web search for job postings uses the built-in reader unless `WEB_ACCESS_PROVIDER` and a key are set.
- **Scheduled job searches** run inside the server process, checked once a minute, so they only run while the copy is running.
- **Rate limits** (sign-in, PDF downloads, AI requests) are kept in the server's memory. The app trusts forwarding headers only from the proxies in `TRUSTED_PROXIES`, which is empty, so its own limits count every visitor as the address Tofu's proxy connects from; sign-in limits read the `X-Real-IP` header. If several instances of the copy run, each counts on its own. `REDIS_URL` shares them, and the resume updates above, across instances.
- **The homepage** (`/`) is upstream's own page about Reactive Resume. Its star count is read from GitHub's API. `ROOT_RESUME_ID` (a resume's ID from `/builder/<id>`) shows one shared resume at `/` instead.
- The server runs as root (see `tofu-entrypoint.sh` above).
